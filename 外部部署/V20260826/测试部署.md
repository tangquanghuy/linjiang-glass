# 测试部署 —— 在真机上验证还没上线的改动

这份文档记的是一件事：**怎么让一份还没上线的改动在真机 / 模拟器上被完整验证，而生产环境一个
字节都不动。**

## 为什么需要它

状态栏这套东西是**两半各自部署**的，而且更新节奏完全不同：

| | 部署方式 | 生效时机 |
|---|---|---|
| 粘贴的那半（本目录下的文件） | 复制粘贴进角色卡 / 酒馆助手 | 粘下去立刻生效，跟 git 无关 |
| HUD（`src/*` 的构建产物） | GitHub Pages | 只从 `main` 构建 |

于是想在手机上验 HUD 侧的改动（视觉性能档、贴图、设置页……），以前只有两条路，两条都不通：

- **合并到 `main`** —— 等于对所有玩家上线。没验过就上线，顺序反了。
- **把 `HUD_URL` 指到本机** —— 要和手机同网段、要开着 dev server，反复用很别扭；而且
  `npm run dev` 每个模块单独发一遍（几百个请求），在低端机上首屏比生产**更慢**，量出来的数字
  没有意义，还会让人误判「改了没用」。

一个仓库只有一个 Pages 站点，生产那个绑在 `linjiang-glass` 的 `main` 上。所以第三条路是：
**再要一个仓库，让它的 Pages 当预览用的 HUD 地址。**

## 两个仓库的分工

| | 仓库 | Pages | 谁在用 |
|---|---|---|---|
| 生产 | `tangquanghuy/linjiang-glass` | `tangquanghuy.github.io/linjiang-glass` | 玩家 |
| 测试镜像 | `tangquanghuy/linjiang-dev` | `tangquanghuy.github.io/linjiang-dev` | 只有你，验证用 |

镜像仓库里放的是 `dev` 分支的**单提交快照**，不是源码，也不推历史（本仓库 `.git` 有 775MB，
大量图片产物进过历史；镜像只需要「现在这份代码」）。每次发布 force push 覆盖，它的历史永远
只有一个提交 —— **它是产物，不是源头，永远不要从它往生产提交。**

镜像的构建同样开 `ASSET_CDN=1`，也就是素材仍然走 `linjiang-glass@main` 那一份。这一点是刻意
的：素材（`bg-plate.png` 2MB、`frost.png` 1MB）走 Pages 在国内实测要 178~240 秒甚至超时失败，
走 jsDelivr 是几秒。让预览站自己扛素材，会把一份生产根本不存在的下载等待掺进测量里，比较就
失去了意义。

## 首次设置（只做一次）

在镜像仓库 `Settings → Pages` 把 **Source 设成 `GitHub Actions`**。

下面那两张卡片（GitHub Pages Jekyll / Static HTML）**什么都不要选** —— 那是「要不要用我们给的
模板工作流」，而镜像里已经带了自己的 `.github/workflows/pages.yml`（模板在本仓库
`scripts/preview-mirror/`，受版本控制，不靠记忆维护）。选了反而会覆盖掉。

## 每次验证的流程

```
node scripts/publish-hud-preview.mjs           # 推快照到镜像 + purge CDN，Actions 自动构建部署
node scripts/make-preview-deploy.mjs --verify  # 生成整套预览部署文件并逐个验地址
```

产物在 `artifacts/preview/`（在 `.gitignore` 里，是本机产物）。把里面的文件粘进一张**测试
角色卡**，对应关系跟生产完全一样：

| 文件 | 粘到哪 |
|---|---|
| `状态栏-测试版-流内嵌入.html` | 角色卡「状态栏」（**当前基准版**） |
| `状态栏.html` / `状态栏-引导壳.html` | 同上，另外两种投递方式 |
| `正文美化.html` / `正文美化-外链素材版.html` | 正文美化的正则模板 |
| `开局.html` | 开局消息 |
| `封面.html` | 封面 |
| `辅助计算脚本.js` / `格式修复脚本.js` / `素材缓存脚本.js` / `小手机脚本.js` | 酒馆助手脚本库 |

**HUD 那一半是自动的**：改完代码只跑 `publish-hud-preview.mjs` 就行，粘贴的文件不用重新粘 ——
除非粘贴文件本身也改了。

## 外链是怎么改写的

只有两条规则，都只动「仓库名」那一段：

| | 生产 | 预览 |
|---|---|---|
| Pages | `tangquanghuy.github.io/linjiang-glass` | `tangquanghuy.github.io/linjiang-dev` |
| jsDelivr | `gh/tangquanghuy/linjiang-glass@main` | `gh/tangquanghuy/linjiang-dev@main` |

host 一律不动：Pages 两边同域；jsDelivr 必须保持 `testingcf`（`cdn.jsdelivr.net` 在国内被墙）。

哪个文件改了什么：

| 文件 | 改写内容 |
|---|---|
| `开局.html` | Pages×1（`opening.html`）+ jsDelivr×3（三张素材） |
| `正文美化-外链素材版.html` | Pages×1（城市底图）+ jsDelivr×2（外链样式表） |
| `正文美化.html` | Pages×1（城市底图） |
| `辅助计算脚本.js` | Pages×1 + jsDelivr×1（`aux-shell.js`） |
| `状态栏.html` / `状态栏-测试版-流内嵌入.html` | Pages×1（`HUD_URL`） |
| `状态栏-引导壳.html` | jsDelivr×1（`status-shell.js`） |
| `素材缓存脚本.js` | **无需改写** —— 里面只有主机白名单，没有仓库名，两个环境主机相同 |
| `小手机脚本.js` / `封面.html` / `格式修复脚本.js` | 无生产外链 |

**只改状态栏一份是不够的**：正文美化要取城市底图和外链样式表，开局要取三张素材，辅助计算脚本
要取 `aux-shell.js`。任何一条还指着生产，验的就是「新壳层配旧资源」—— 一个现实中不存在的组合，
而且出问题时根本分不清是哪一半坏的。

## 怎么确认手机上跑的是预览版

状态栏 → 全局设置 → 拉到底，有一行小字：

```
HUD <git 短 sha>     壳层 <SHELL_VERSION>     原生流 / 抬升
```

- **HUD** 告诉你镜像站部署到了哪一版；
- **壳层** 告诉你粘的是哪一版 —— 这是最容易搞错的一半，因为它冻结在你粘贴那一天；
- **架构** 移动端应该是「原生流」。显示「抬升」说明架构判定没命中，那一半性能改动全都没生效。

另一个无需控制台的判据：原生流下全局设置里**不应该有**「HUD 停靠方式」那一项（原生流没有
"停靠"这个概念，设置页会把它藏掉）。

## 设计决定，以及为什么

### 预览文件从 git 读，不从工作区读

镜像是 `dev` 的快照。如果预览文件从工作区生成，而工作区里有别人正在改的东西，预览就会 404 在
一个跟被测改动毫无关系的地方 —— 现场看起来像「新代码坏了」。

这不是假设：实测撞到过 `正文美化-外链素材版.html` 已经指向 `reading.0697f41a.css`，而那个文件
还没提交，镜像里根本没有。

所以一律 `git show <ref>:<path>`，跟镜像同源；工作区与 ref 不一致时脚本会明确警告，而不是悄悄
用了另一份。

### 换行符按工作区那一份还原

`git show` 吐仓库里存的 LF，而这批粘贴产物在工作区是 CRLF（`scripts/build-status-shell.mjs`
刻意的）。不还原的话，被测物和线上物逐字节不同 —— 大概不影响功能，但「被测物和线上物不是同
一份」这种事不该主动引入。

### 发布时必须 purge jsDelivr

`状态栏-引导壳.html` 和 `辅助计算脚本.js` 是**直接从 jsDelivr 取**脚本的，而镜像每次 force
push 一个新提交、`@main` 这种可变引用有 12 小时边缘缓存。不 purge 就会继续吃旧版，而且**毫无
迹象**：不报错、不提示，只是行为对不上代码。生产的 `.github/workflows/pages.yml` 里有同样一步，
理由也写在那儿。

### `--verify` 为什么值得有

它把改写后的每个地址请求一遍。加上它的当天就抓到两个错，两个都会在真机上表现成「无关的地方
404」：

1. **以 `/` 结尾的是前缀，不是资源。** `正文美化` 里 `city/plate/` 后面是运行时按事件类别拼
   上去的文件名。直接 HEAD 一个目录，Pages 一律 404 —— 而**生产的同一个地址也是 404**，也就是
   说那是检查错了，不是部署坏了。改成给前缀取一个真实子文件再验。
2. **样本必须从 git 取，不能从磁盘取。** `city/plate/*` 整个在 `.gitignore` 里（磁盘上 22 个
   文件、被跟踪的只有 11 个），从磁盘挑到的 `dongtang_night.png` 根本进不了任何部署。用
   `git ls-tree` 取样，验的才是「真能部署出去的那些」。

## 这套办法验不到什么

说清楚边界，免得把「夹具全绿」当成「真机没问题」：

- **弱 GPU 的合成带宽。** 本地夹具跑在桌面 GPU 上，CPU 限速不影响光栅，而 `backdrop-filter`
  和大贴图的成本恰恰在光栅。这是必须上真机的主要原因之一。
- **1GB 内存的压力。** GC 抖动、贴图被反复驱逐重解码，夹具完全没建模。
- **国内网络的真实延迟。** 镜像的 Pages 和生产的 Pages 是同一个基础设施，这一项是可比的；但
  素材走的是 `linjiang-glass@main`，跟生产一致，所以也别指望在预览里发现"素材变慢了"这类问题。

## 不要做的事

- 不要把 `artifacts/preview/` 里的文件粘到**正式**角色卡上。它们指向镜像站，而镜像站随时会被
  下一次快照覆盖。
- 不要从镜像仓库往生产提交。它是单向快照，历史会被 force push 覆盖。
- 不要在镜像仓库里改代码。改了下一次发布就没了。
