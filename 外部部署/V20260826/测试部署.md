# 测试部署 —— 在真机上验证还没上线的改动

这份文档记的是一件事：**怎么让一份还没上线的改动在真机 / 模拟器上被完整验证，而生产环境一个
字节都不动。**

## 为什么需要它

状态栏这套东西是**两半各自部署**的，而且更新节奏完全不同：

| | 部署方式 | 生效时机 |
|---|---|---|
| 粘贴的那半（本目录下的文件） | 复制粘贴进角色卡 / 酒馆助手 | 粘下去立刻生效，跟 git 无关 |
| HUD（`src/*` 的构建产物） | GitHub Pages | 只从 `main` 构建 |

于是想在手机上验 HUD 侧的改动（视觉性能档、贴图、设置页……），以前只有两条路，两条都不通：

- **合并到 `main`** —— 等于对所有玩家上线。没验过就上线，顺序反了。
- **把 `HUD_URL` 指到本机** —— 要和手机同网段、要开着 dev server，反复用很别扭；而且
  `npm run dev` 每个模块单独发一遍（几百个请求），在低端机上首屏比生产**更慢**，量出来的数字
  没有意义，还会让人误判「改了没用」。

一个仓库只有一个 Pages 站点，生产那个绑在 `linjiang-glass` 的 `main` 上。所以第三条路是：
**再要一个仓库，让它的 Pages 当预览用的 HUD 地址。**

## 两个仓库的分工

| | 仓库 | Pages | 谁在用 |
|---|---|---|---|
| 生产 | `tangquanghuy/linjiang-glass` | `tangquanghuy.github.io/linjiang-glass` | 玩家 |
| 测试镜像 | `tangquanghuy/linjiang-dev` | `tangquanghuy.github.io/linjiang-dev` | 只有你，验证用 |

镜像仓库里放的是**当前工作区的单提交快照**，不是源码，也不推历史（本仓库 `.git` 有 775MB，
大量图片产物进过历史；镜像只需要「现在这份代码」）。每次发布 force push 覆盖，它的历史永远
只有一个提交 —— **它是产物，不是源头，永远不要从它往生产提交。**

### 快照的是工作区，不是某个提交

这一点值得单独说，因为它跟直觉相反、而且改过一次。

原来两个脚本都只认已提交的 `dev`：镜像 `git archive dev`，预览文件 `git show dev:<path>`。
理由是"两边同源，避免 404 在无关的地方"。但那套组合和这个仓库存在的唯一目的相反 —— 镜像是
用来验**还没上线、通常也还没提交**的改动的。

实测撞到过：工作区的 `正文美化-外链素材版.html` 已经指向 `reading.0697f41a.css`，而那个文件
还没提交；于是预览文件从 git 读到的是旧的 `reading.bab922d8.css`，手机上验的是**上一版配色**，
而且连 404 都不报。这是最坏的一种失败：安静地验错东西。

现在两个脚本默认都快照工作区（`git ls-files -c -o --exclude-standard`，即「已跟踪 + 未跟踪但
不被 `.gitignore` 忽略」）。「两边同源」这个前提仍然成立，只是基准从"某个提交"变成"磁盘上现在
这份"；未提交的文件现在**在**镜像里，404 那个担心自动消失。

所以**改完代码不用先提交**就能发预览。要回到"只发已提交的那一版"，两个脚本都加 `--ref=dev`。
`.gitignore` 仍然被尊重，`node_modules` / `dist` / `artifacts` 不会进镜像。

镜像的构建同样开 `ASSET_CDN=1`，也就是素材仍然走 `linjiang-glass@main` 那一份。这一点是刻意
的：素材（`bg-plate.png` 2MB、`frost.png` 1MB）走 Pages 在国内实测要 178~240 秒甚至超时失败，
走 jsDelivr 是几秒。让预览站自己扛素材，会把一份生产根本不存在的下载等待掺进测量里，比较就
失去了意义。

## 首次设置（只做一次）

在镜像仓库 `Settings → Pages` 把 **Source 设成 `GitHub Actions`**。

下面那两张卡片（GitHub Pages Jekyll / Static HTML）**什么都不要选** —— 那是「要不要用我们给的
模板工作流」，而镜像里已经带了自己的 `.github/workflows/pages.yml`（模板在本仓库
`scripts/preview-mirror/`，受版本控制，不靠记忆维护）。选了反而会覆盖掉。

## 每次验证的流程

```
node scripts/publish-hud-preview.mjs           # 推快照到镜像 + purge CDN，Actions 自动构建部署
node scripts/make-preview-deploy.mjs --verify  # 生成整套预览部署文件并逐个验地址
```

产物在 `artifacts/preview/`（在 `.gitignore` 里，是本机产物）。把里面的文件粘进一张**测试
角色卡**，对应关系跟生产完全一样：

| 文件 | 粘到哪 |
|---|---|
| `状态栏-测试版-流内嵌入.html` | 角色卡「状态栏」（**当前基准版**） |
| `状态栏.html` / `状态栏-引导壳.html` | 同上，另外两种投递方式 |
| `正文美化.html` / `正文美化-外链素材版.html` | 正文美化的正则模板 |
| `开局.html` | 开局消息 |
| `封面.html` | 封面 |
| `辅助计算脚本.js` / `格式修复脚本.js` / `素材缓存脚本.js` / `小手机脚本.js` | 酒馆助手脚本库 |

**改完代码不用先提交**，直接跑上面两条命令就行（镜像快照的是工作区，见前面那一节）。

哪些粘贴文件需要重新粘：

| 改了什么 | 要重新粘吗 |
|---|---|
| `src/*`（HUD） | 不用。HUD 从镜像 Pages 取，地址固定 |
| `public/shell/status-shell.js`（壳层） | 用 `状态栏-引导壳.html` 的话**不用**（壳层脚本也从镜像 Pages 取）；用自包含的 `状态栏.html` / `状态栏-测试版-流内嵌入.html` 就必须重新粘，因为壳层是内联进去的 |
| 粘贴文件本身 | 要 |

也就是说：想省掉"每次改壳层都重新粘"，用 `状态栏-引导壳.html`。

## 外链是怎么改写的

三条规则：

| | 生产 | 预览 |
|---|---|---|
| Pages（HUD） | `tangquanghuy.github.io/linjiang-glass` | `tangquanghuy.github.io/linjiang-dev` |
| 壳层脚本 | `jsDelivr …@main/public/shell/` | `tangquanghuy.github.io/linjiang-dev/shell/` |
| 素材 | `gh/tangquanghuy/linjiang-glass@main` | `gh/tangquanghuy/linjiang-dev@main` |

Pages 两边同域，只换项目名；jsDelivr 必须保持 `testingcf`（`cdn.jsdelivr.net` 在国内被墙）。

### 壳层脚本为什么换成走 Pages

这是一个会静默骗人的坑，实测数据留在这里。镜像每次都是 force push，而 jsDelivr 对 `@main`
这种可变引用**除了文件缓存，还另有一层「分支 → 提交」的映射缓存**。同一时刻、同一个路径：

| 取法 | 字节 | 是否含刚推上去的改动 |
|---|---|---|
| jsDelivr `@main` | 177613 | ❌ |
| jsDelivr `@<完整 sha>` | 187247 | ✅ |
| `raw.githubusercontent` | 187247 | ✅（证明仓库内容本身没问题） |
| 镜像 Pages `/shell/…` | 187247 | ✅ |

purge 两次都返回 `finished`，文件也确实从 153684 变成了 177613 —— 也就是 purge 生效了，但映射
仍停在上一个提交。表现是最坏的那种：不报错、不提示，只是手机上跑的不是你刚写的代码。

**为什么选 Pages 而不是钉 sha。** 钉 sha 也正确，但 sha 每次发布都变，于是
`状态栏-引导壳.html` 和 `辅助计算脚本.js` 每次都得重新粘 —— 而这两个文件存在的意义恰恰是
"粘一次就不用再动"。镜像 Pages 的地址固定，每次 Actions 部署就是最新的，两头都要到了；
Pages 也正是 `HUD_URL` 已经在用的通道，没引入新依赖。

**素材不走这条路**，仍然留在 jsDelivr：素材大（`bg-plate.png` 2MB），走 Pages 在国内实测
178~240 秒。而素材的陈旧风险很小 —— `reading.<hash>.css` / `banner-<hash>.webp` 这类内容哈希
文件一改就换路径，jsDelivr 从没缓存过那个新路径，天然免疫；剩下 3 张不带哈希的开局图基本是
静态的，`publish-hud-preview.mjs` 每次会把它们一起 purge。

哪个文件改了什么：

| 文件 | 改写内容 |
|---|---|
| `开局.html` | Pages×1（`opening.html`）+ jsDelivr×3（三张素材） |
| `正文美化-外链素材版.html` | Pages×1（城市底图）+ jsDelivr×2（外链样式表） |
| `正文美化.html` | Pages×1（城市底图） |
| `辅助计算脚本.js` | Pages×1 + 壳层脚本×1（`aux-shell.js`） |
| `状态栏.html` / `状态栏-测试版-流内嵌入.html` | Pages×1（`HUD_URL`） |
| `状态栏-引导壳.html` | 壳层脚本×1（`status-shell.js`） |
| `素材缓存脚本.js` | **无需改写** —— 里面只有主机白名单，没有仓库名，两个环境主机相同 |
| `小手机脚本.js` / `封面.html` / `格式修复脚本.js` | 无生产外链 |

**只改状态栏一份是不够的**：正文美化要取城市底图和外链样式表，开局要取三张素材，辅助计算脚本
要取 `aux-shell.js`。任何一条还指着生产，验的就是「新壳层配旧资源」—— 一个现实中不存在的组合，
而且出问题时根本分不清是哪一半坏的。

## 怎么确认手机上跑的是预览版

状态栏 → 全局设置 → 拉到底，有一行小字：

```
HUD <git 短 sha>     壳层 <SHELL_VERSION>     原生流 / 抬升
```

- **HUD** 告诉你镜像站部署到了哪一版；
- **壳层** 告诉你粘的是哪一版 —— 这是最容易搞错的一半，因为它冻结在你粘贴那一天；
- **架构** 移动端应该是「原生流」。显示「抬升」说明架构判定没命中，那一半性能改动全都没生效。

另一个无需控制台的判据：原生流下全局设置里**不应该有**「HUD 停靠方式」那一项（原生流没有
"停靠"这个概念，设置页会把它藏掉）。

## 设计决定，以及为什么

### 镜像和预览文件都快照工作区，而不是某个提交

完整理由在前面「快照的是工作区，不是某个提交」那一节。一句话：镜像存在的目的是验还没上线、
通常也还没提交的改动，所以基准必须是磁盘上现在那份，否则会安静地验错东西。

关键是**两边必须同一个基准**。以前两边都是 `dev`，同源；现在两边都是工作区，同样同源。只改
一边才是危险的 —— 那正是 `reading.<hash>.css` 那次的形状（镜像里没有的文件，预览文件却指着它）。

### 换行符只在 `--ref` 模式下还原

`git show` 吐仓库里存的 LF，而这批粘贴产物在工作区是 CRLF（`scripts/build-status-shell.mjs`
刻意的）。不还原的话，被测物和线上物逐字节不同 —— 大概不影响功能，但「被测物和线上物不是同
一份」这种事不该主动引入。

默认的工作区模式不需要这一步：读的就是工作区那一份，本来就逐字节相同。

### purge 仍然做，但预览已经不依赖它了

历史原因：`状态栏-引导壳.html` 和 `辅助计算脚本.js` 原来直接从 jsDelivr 取脚本，而镜像每次
force push、`@main` 有边缘缓存，不 purge 就会静默吃旧版。后来实测发现**purge 救不回来**（那层
「分支 → 提交」的映射缓存不跟着走，数据在前面「壳层脚本为什么换成走 Pages」那一节），所以预览
的壳层脚本改走镜像 Pages 了。

现在 `publish-hud-preview.mjs` 仍然 purge，为两件事：照顾之前已经粘过 `@main` 版本的角色卡；
以及素材仍然走 jsDelivr —— 只列**不带内容哈希**的那几个，带哈希的一改就换路径、天然不会陈旧。

生产那边不受影响，`.github/workflows/pages.yml` 里的 purge 照旧（生产不 force push，`@main`
的映射本来就会前进）。

### `--verify` 为什么值得有

它把改写后的每个地址请求一遍。加上它的当天就抓到两个错，两个都会在真机上表现成「无关的地方
404」：

1. **以 `/` 结尾的是前缀，不是资源。** `正文美化` 里 `city/plate/` 后面是运行时按事件类别拼
   上去的文件名。直接 HEAD 一个目录，Pages 一律 404 —— 而**生产的同一个地址也是 404**，也就是
   说那是检查错了，不是部署坏了。改成给前缀取一个真实子文件再验。
2. **样本必须从「真能进镜像的那些文件」里取，不能直接 readdir 磁盘。** `city/plate/*` 整个在
   `.gitignore` 里（磁盘上 22 个文件、被跟踪的只有 11 个），从磁盘挑到的 `dongtang_night.png`
   根本进不了任何部署。两种模式下"能进镜像"的定义不同，取样口径也跟着变，否则验的还是别的
   东西：`--ref` 模式用 `git ls-tree`，默认的工作区模式用
   `git ls-files -c -o --exclude-standard`（跟 `publish-hud-preview.mjs` 挑文件的口径逐字一致）。

## 这套办法验不到什么

说清楚边界，免得把「夹具全绿」当成「真机没问题」：

- **弱 GPU 的合成带宽。** 本地夹具跑在桌面 GPU 上，CPU 限速不影响光栅，而 `backdrop-filter`
  和大贴图的成本恰恰在光栅。这是必须上真机的主要原因之一。
- **1GB 内存的压力。** GC 抖动、贴图被反复驱逐重解码，夹具完全没建模。
- **国内网络的真实延迟。** 镜像的 Pages 和生产的 Pages 是同一个基础设施，这一项是可比的；但
  素材走的是 `linjiang-glass@main`，跟生产一致，所以也别指望在预览里发现"素材变慢了"这类问题。

## 不要做的事

- 不要把 `artifacts/preview/` 里的文件粘到**正式**角色卡上。它们指向镜像站，而镜像站随时会被
  下一次快照覆盖。
- 不要从镜像仓库往生产提交。它是单向快照，历史会被 force push 覆盖。
- 不要在镜像仓库里改代码。改了下一次发布就没了。
