### 2. 每个角色的 `stream.slots`

`stream` 从三字段扩成带档期：

```js
stream: {
  live: false, title: '', viewers: 0,
  slots: [{ day: '周二', period: '夜' }, ...],
}
```

**核心约定：`slots` 是计划，`live` 是事实，两者允许不一致。**

- `slots` 是 authored 稳定数据（她的作息习惯），手写维护
- `live` 由 `变量相关/辅助计算脚本.js`（tavern 脚本，不是这个 iframe）回写
- 不一致本身是有价值的信息，不是脏数据：周五夜有档期而 `live` 为 false，就是「今日休播」

样本数据刻意让六种状态各出现一次，页面开发时不需要自己造测试数据。当前世界时间是 **周五 · 夜**：

| 角色 | 档期 | 今天(周五 夜)落在的状态 |
|---|---|---|
| 塔菲 | 周一/三/五 夜、周六 昼+夜 | `live` 正在播 |
| 璃亚梦 | 周三/五/六/日 深夜 | `unplanned` 临时开播(夜) + `booked` 档期(深夜) |
| 东雪莲 | 周二 夜、周五 夜、周日 昼 | `off` 休播 |
| 斯黛拉 | 周二/四/六 暮 | 空 |
| 红蔷薇 | 周四/日 暮 | 空 |
| 沙花叉 | 周六/日 深夜 | 空 |
| 时雨羽衣 | `[]` | 整行空 |

两个样本设置是刻意的，别「顺手修掉」：

- **时雨羽衣 `slots: []`** — 她不是主播。空列表是页面必须渲染的状态，不是待填的洞。一行全空就是页面在说「她不开播」。
- **红蔷薇 `fan()` 但有档期** — `fan` 是玩家在她频道上的账号，`slots` 是她自己的班表。两者无关。保留一个「她开播、玩家没关注」的样本，防止网格被误读成「只显示我关注的人」。

### 3. `SLOT_STATES`

六种格子状态及各自的 label 与 tone：

| key | label | 含义 |
|---|---|---|
| `live` | 正在播 | 事实 = 计划 |
| `unplanned` | 临时开播 | 计划外开播 |
| `off` | 休播 | 计划内但当前时段没播 |
| `booked` | 档期 | 未来时段的计划 |
| `past` | 未开播 | 今天更早的时段有档期但人没出现 |
| （null） | — | 这格没有她 |

放在 `data.js` 而不是任一页面里，理由和 `workBadge` 的四种到岗状态一样：「这格是什么」是档期与直播之间的契约规则，不是表格或点阵的属性，两套布局不能给出不同答案。

`past` 与 `off` 刻意分开：休播是对「现在」的判断，一个时段之前只是历史。两者都画得很淡，但页面有能力区分。

### 4. `streamSchedule()`

7 天 × 5 时段 × 7 人，一个模型，同时给出两种切法：

```js
{
  weekday, now, nowIndex,
  days,       // [{ day, isToday }] × 7
  periods,    // PERIODS
  grid,       // grid[时段索引][天索引] = [格内角色...]
  todayRows,  // [{ period, isNow, isPast, entries }] × 5
  liveNow,    // 处于 live / unplanned 的角色，给表头计数
}
```

格内每个角色条目：`{ name, romaji, theme, state, title, viewers, watching }`。`title` / `viewers` 只在两种 live 状态下有值，档期格还没有房间标题。

同时返回 `grid` 和 `todayRows`，是因为两套布局要的是同一件事的不同切面，谁都不该去转置对方的形状——见第三节的空间量测。

### 5. `scheduleHint(model?)`

给入口行用的一句摘要，形如 `5 人有档期 · 在播 2 · 休播 1`。

## 二、与原方案的两处偏差

1. **没有加 `offToday` 字段。** 「今日休播」完全能从 `slots` + `live` + 当前时段推出，不需要额外字段。真正需要它的场景是「她发布了停播公告」——那是另一种数据，目前没有消费者，先不发明。

2. **`live` 只能落在当前时段格。** schema 里 `live` 是不带时段的裸布尔值，所以无法知道她今天昼时段播过没有。代码注释里写明了这条限制，没有伪造历史——和 `sortedEvents` 对「区域邻接」的处理是同一个判断（`区域` 是格式化字符串，schema 里没有邻接关系，所以不假装能算距离）。

如果将来要历史，需要 schema 侧先给出带时段的直播记录，不是在 HUD 里推。

## 三、未完成：页面层

### 已量测好的空间约束（不用重新测）

**横屏** — `.page-modal` 固定 1520×820，body 去掉 padding 后 **1406×654**：

```
时段标签列 100  →  每天列 187 × 每行 131
```

187×131 很宽裕，**放得下角色名，不只是色点**。所以横屏一屏就是完整一周，今天那一列高亮，**不需要状态切换**——这才是把多出来的空间用对了。

**竖屏** — 面板内宽 **795 单位**（k=0.414 @ 390px 视口）：

```
7 列 + 120 单位时段标签  →  每列 96 单位 = 39.9 真实像素
三字名字 @ --fs-micro(36)  →  光文字就要 108 单位 = 44.7 真实像素
```

**竖屏装不下带名字的周视图。** 所以拆成两段堆叠：

1. 上半：7×5 **纯色点矩阵**（96 单位的列放 40 单位的点很舒服），只给「这周的形状」
2. 下半：**今日 5 个时段的展开列表**，带完整名字、标题、人数

这是代码库已有的分歧模式——`eventsPage`、`relationsPage`、背包（页 vs 抽屉）在两套布局里都各写一份，`.pcard-status` 的注释也明说过「sharing one row does not work here」。

**为什么用色点而不是数字网格**：7×5=35 格里同时开播的通常只有 1~3 个，纯网格会有 80% 空格。`.t-*` 代表色系统（`--rim` / `--wash` / `--glow` / `--ornament`）玩家已经在卡片、dock、状态栏 chip 上学过七次，一格放一颗她的颜色点就是「一眼看进去的形状」。空格也是信息：她周三不播。这与代码库里反复出现的主张一致——「twelve digits in a grid is a list you have to read value by value to find the two that are not zero, whereas twelve bars is a shape you take in at once」。

## 四、路上发现的、与本功能无关的既有问题

这三条都不是本次改动引入的，也都没有处理：

1. **`羁绊总览` 没有任何 UI 入口。** `relationsPage` 在两套布局都实现了、都注册了路由（`src/pages.js` 约 715 行、`PORTRAIT_PAGES`），但 `tools` 里没有它，也没有任何 `data-page="relations"`，只能靠 `pages.open('relations')` 从代码里调。做第 2 步入口时可以顺手一起解决。

2. **横屏 `eventsPage()` 没有用 `sortedEvents()`。** 它仍然直接 `dailyEvents.map(...)`（`src/pages.js` 约 343 行），按 authored 顺序渲染；竖屏的 `eventsPage()` 已经改用 `sortedEvents()` 了。`data.js` 里 `sortedEvents` 的注释说明了排序规则（可触发 > 同区域 > 优先级）本就该由数据层拥有，所以横屏这处是漏改。

3. **手机横屏字号只有 6.6 真实像素。** `npm run responsive` 会报 `smallest landscape type lands at 6.6 real px (floor 13)`。这是既定取舍而不是失败——横屏画布尺寸固定 + cover 缩放，手机横屏 k=0.505，`--fs-micro` 13 × 0.505 = 6.6。脚本自己只打印不断言，注释里写明这是「数字定不了的问题」，需要人眼判断，看 `artifacts/landscape-phone.png`。要处理的话是另一件事：给横屏画布加 k 下限，或者给手机横屏单独一档字号。
