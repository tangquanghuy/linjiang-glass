# 直播间状态机 · 规则说明

本文描述「后台怎么算、什么进 MVU、什么给 AI 看」。已实现的部分以代码为准，
未实现的标了「未做」。

---

## 1. 职责划分（最重要的一条）

- **`外部部署/V20260826/辅助计算脚本.js`** 拥有直播间的**全部**表、算法和写入。
  礼物价格、人气点数、体量曲线、NPC 对手、热度涨落、榜与大航海，都只在这里。
- **`外部部署/V20260826/正文美化.html`** 只负责画。它不存表、不算数、不写 MVU，
  只通过 `parent.LinjiangAux` 的三个口子说话（同源，不用 postMessage）：

  | 口子 | 干什么 |
  |---|---|
  | `roomMenu()` | 礼物栏要画的东西：价格、人气点数、图标 URL、数量档位、醒目留言档位 |
  | `roomView(名)` | 挂载时读一次的快照。顺手把这间房的对手种上（只第一次） |
  | `roomAction({...})` | 玩家的每一个动作。返回 `{ ok, 花费, 人气, 还手, 快照 }` |

  拿不到脚本时卡片退化成只读，按钮提示「辅助计算脚本没跑起来」，
  **不自己算一套兜底** —— 那是两份公式打架的开始。

- **`opening.html` / `opening.js`**（开局页）只在开局那一次写初始值。
  它托管在 GitHub Pages、跨域拿不到辅助脚本，所以体量曲线在那边有一份**镜像**；
  `scripts/check-stream-scale.cjs` 逐档比对两份实现，漂了就失败。

## 2. 给 AI 看 / 只给后台

`对象信息.<名>.直播` 给 AI 看，`系统配置.直播间.<名>` 只给后台。
变量注入默认不把 `系统配置` 这棵树摊给模型。

| | 给 AI（`对象信息.<名>.直播`） | 只给后台（`系统配置.直播间.<名>`） |
|---|---|---|
| 开不开播、标题 | `开播` / `标题` | — |
| 房间规模 | `热度`：底盘 + 本场虚火，收成约数 | `底盘热度`、`本场热度` |
| 她有多少粉 | `粉丝数`：稳定量，公开事实 | `体量档位` |
| 玩家粉籍 | `玩家信息.粉丝身份.<名>` | — |
| 人在哪间房 | `玩家信息.所在直播间` | — |
| 大航海 | 不写 | `大航海`：三档人数 + 具名名单 |
| 高能榜 | 不写 | `高能榜`：NPC + 玩家本场消费 |
| 对手 | 不写 | `种子`、`还手预算`、`还手次数`、`连送` |
| 顶栏文案 | 不写 | `档期`、`牌子名` |

**直播间没有人数，只有热度。** `直播.人数` 这个字段已经删除。
旧档里读到 `人数` 会被 `mvuzod.js` 的 `streamSchema` 搬成 `热度`。

`变量更新规则` 里 `直播.热度`、`直播.粉丝数`、`系统配置.直播间` 都在 `脚本只读` 名单里。

图片地址一律不进 MVU（太占地方），见 §8。

## 3. 体量：粉丝数是唯一的作者定值

一个主播有多大，只由**粉丝数**决定；底盘热度和大航海全是它的函数。
存两份就一定会漂，而且哪份准没人说得清。

定义在 `辅助计算脚本.js`：

```js
streamScale(体量档位)        // 档位 0–100 → { 粉丝数, 底盘热度, 舰长数, 提督数, 总督数 }
tierOfFollowers(粉丝数)      // 反解档位（曲线单调，扫 0–100 取最近的 0.1 档）
scaleOfFollowers(粉丝数)     // 上面两个串起来
```

```
底盘热度 = 50 × 8^(档位/25)                    每 25 档翻 8 倍
粉丝数   = 底盘热度 × (60 − 0.42×档位)          比值随体量下降：小主播 60 倍、头部 18 倍
舰长数   = 粉丝数 × (0.0012 + 0.000038×档位)    0.12% → 0.5%
提督数   = max(0, ⌊(舰长数 − 40) / 24⌋)         减门槛再除，小房干净归零
总督数   = max(0, ⌊(舰长数 − 300) / 260⌋)
```

粉丝／热度比**随体量下降**是因为小直播间靠路人堆关注数，大直播间本来就留得住人。
提督（1998/月）和总督（19998/月）要稀：这里的比值比初版草案更保守
（舰长:提督 24:1、舰长:总督 260:1，初版是 15:1 和 60:1）。

## 4. 开播、下播、档期

档期分两处，各有各的用途：

- **开播判定**用 `辅助计算脚本.js` 里的 `STREAM_HABITS`（周几、起止、准时率、突发率、标题池）。
  这是冷代码要算的东西，不进 MVU，避免模型改她周几休。
- **顶栏文案**用 MVU 的 `系统配置.直播间.<名>.档期`（例如「晚间主档 20:00–23:30」）。
  卡片直接读，不在展示层写死。

跨零点的档（东雪莲、沙花叉、时雨羽衣、璃亚梦）按「开始 ≥ 现在或现在 ≤ 结束」算在窗里。

四种状态与日程表一致：**正在播 / 临时开播 / 今日休播 / 固定档**。
`driveStreams` 用日期种子投骰，同一游戏日反复刷新结果一致，换日才重投。
AI 在正文里明确改写直播字段时，当天的自动结果让位（`streamManualLocks`）。

下播或换日：

- `本场热度` 清零，`直播.热度` 清零，`标题` 清空。
- **`底盘热度` 和 `粉丝数` 不清** —— 那是这个人的常态，不是这一场的账。
- 高能榜本场消费保留到下次开播前被覆盖；大航海人数只随办卡和到期缓变。
- 玩家的 `累计打赏`、`牌子档位` 留在 `粉丝身份`。

> 注意 `变量初始化` 的日期是 2026年4月1日 = **周三**，正好是塔菲的休播日。
> 写测试时如果要她在播，得把日期挪到周四并对上 20:00–23:30。

## 5. 热度怎么涨（核心）

热度不是人数的别名，也不是一条直线。

**`直播.热度` = `底盘热度` + `本场热度`**，收成约数写给 AI。
`底盘热度` 礼物永远不动它；礼物只往 `本场热度` 这团虚火上加。

### 5.1 单笔换算

金额当燃料，但不是 1 元 1 点。表在 `辅助计算脚本.js` 的 `GIFTS` / `GUARD_BUY`，
一件东西一行（价格 + 人气点数 + 图标文件），以前这三样分在三张表里。

| 东西 | 金额 | 人气点数 |
|---|---|---|
| 小心心 | 0 | 2 |
| 辣条 | 1 | 8 |
| 干杯 | 20 | 70 |
| 心愿盲盒 | 50 | 150 |
| 情书 | 100 | 400 |
| 小飞机 | 200 | 900 |
| 摩天大楼 | 520 | 2200 |
| 火箭 | 1288 | 8000 |
| 舰长 | 138 | 500 |
| 提督 | 1998 | 9000 |
| 总督 | 19998 | 40000 |

醒目留言按 `金额 × 4` 折算人气。

### 5.2 连送递减

`comboPop()`，下限 40%（`[1, 0.85, 0.7, 0.55, 0.4]`），两层一起算：

1. **单笔内部**：一次送 n 个，第 2 个起就打折。辣条 ×233 出来 758 点，线性会是 1864。
2. **跨笔**：连续送**同一件**礼物才累计，换一件重置。大航海和醒目留言重置计数。

**不按世界时钟算。** 时钟只有 AI 推进时才动，整场直播可能一直停在同一分钟，
按分钟算会把「辣条→干杯→情书→火箭」这条正常消费链整条打到下限。

### 5.3 衰减

`decaySessionHeat()`。世界时钟每往前走一拍，`本场热度 × 0.9`，
掉到 `底盘热度` 的 1% 以下归零。只处理在播的房间。这是下播前房间「凉下去」的手感。

实测一场火箭之后：

```
第1拍 本场热度 10256 → 直播.热度 28500
第8拍 本场热度  4904 → 直播.热度 23100
```

### 5.4 观众也会带热度（不只玩家）

原来 `本场热度` 只有玩家掏钱才动：玩家全程只看不花钱，一整场热度就钉在
`底盘 × pulse` 上不动，等于「热度只反映玩家投入」。补了两条，都在代码里算，
不进提示词、不让 AI 写。

**一、正文里的 `<LiveRoom>` 弹幕按内容结算**（`settleRoomsFromText`）

那段文本是 AI 必须按 `世界书/直播间卡片规则` 输出的结构化格式，字段固定、
礼物名取自白名单，直接当输入用。为什么不让 AI 直接写热度：热度是
`底盘 + 本场` 的派生量，交给模型必然和这条分界打架（下播该清多少就说不清了），
而且 `变量更新规则` 里 `直播.热度` 本来就在 `脚本只读` 名单上。

| 弹幕类型 | 折算 |
|---|---|
| 普通 / 舰长 / 提督 / 总督 | 每条 `底盘 × 0.15%`，一轮 20 条约 3% |
| 礼物 | `GIFTS` 表的点数 × 数量递减 × 0.6 |
| 醒目留言 | `金额 × 4 × 0.6` |
| 进入 / 系统 | 不计 |

发言用相对量、礼物用绝对量是故意的：绝对值在塔菲（底盘 18200）和璃亚梦（1390）
之间差十三倍，一条发言写死几点对小房是洪水、对塔菲是噪音；而一发火箭在小房
掀翻天是应该的。观众礼物打 0.6 折是为了让玩家自己送的那一发更有分量。

两道闸：一轮最多计入 **6 条**礼物弹幕（卡条数比卡点数直观，防 AI 一口气写六个
火箭），总增量上限 `底盘 × 1.5`。白名单外的礼物名直接不算。

**幂等靠标记**，记在 `系统配置.直播间.<名>.本场结算 = "<楼层>:<指纹>"`。
`isProcessing` 那个防重入标志防的是脚本改完变量又被 schema reconciliation 二次唤起
的递归，同一条消息在别的场合还是会再过一遍：swipe、重 roll、编辑楼层、切聊天重进
都会让 `VARIABLE_UPDATE_ENDED` 再来一次。本文件其余写入都是「按状态重算」
（热度 = 底盘+本场、牌子等级 = f(累计打赏)），重算多少次结果一样；而「数弹幕再累加」
是纯增量，多跑一次就多加一次。swipe 换了内容指纹就变，会重新结算 —— 那是另一个
分支的剧情，应该重算。下播时标记跟 `本场热度` 一起清。

**二、所有在播的房间每拍加一点环境流量**（`ambientHeat`）

跟玩家在不在看无关 —— 路人进出本来就该有起伏，代码算这个没成本。
每拍 `+底盘 × (0~6%)`，抖动用 `(种子|时钟)` 做哈希，同一拍算出来是同一个值。
和 `decaySessionHeat` 共用「时钟真往前走了」那道门（这道门本身幂等：同一轮里
before/after 时钟一样就整段跳过），顺序是先衰减后加，反过来新加的当拍就被削一成。

配 0.9 衰减，`本场热度` 收敛在底盘的三成左右，总热度在底盘的 **1.28 倍**附近浮动。
`scripts/check-room-heat.cjs` 跑 60 拍量的：东雪莲底盘 8830，尾段均值 2516（28%）。

### 5.5 「在线人数」不做

初版草案里 `人气` 和 `在线` 是两个数，还有一条 log10 的追随公式。
现在只有热度一个数 —— 直播间没有人数这个概念。

## 6. NPC 对手（高能榜）

`seedRoom()`。玩家第一次进这间房时生成，之后只更新、不重抽。
种子存进 `系统配置.直播间.<名>.种子`，所以重进房间对手还是那几个人。

- **数量** 4~7 个，名字从 `NPC_NAMES` 抽（临江地名 + 生活状态的调子，
  例如「云庭7楼」「西洲加班人」「洲门站末班」，不要平台网名腔）。
- **榜一开工消费** = `底盘热度 × 4%`，夹在 40~900。
  塔菲那档约 660，璃亚梦那档约 56。
- **往下递减** `榜一 × 0.62^i`，再乘一点抖动（0.8~1.2）。
  0.62 这个比例是为了让榜首和榜二有明显差距，否则玩家一笔就连超三个人。

实测塔菲房：

```
1.西洲加班人 ￥657  2.梧桐里租客 ￥408  3.落霞后街 ￥253  4.明湖环洲 ￥157
```

一整轮消费下来：辣条→干杯→情书 才爬到第 5，小飞机第 3，**得送火箭才抢到榜一**。
这就是「送一杯干杯上不了第一」的手感。

### 6.1 还手

`rivalStrikeBack()`。玩家用**单笔 ≥ 100** 抢走榜一后：

- 约**三成**机会，榜一 NPC 立刻回一笔（20~300，够反超就行）。
- 吃 `还手预算`（= 榜一开工消费 × 2~4），用尽就认输。防止 NPC 钱包无限。
- 还手也会推 `本场热度`（金额 × 3.5）。
- **总督级还手禁止**，NPC 不办提督/总督来压玩家。

掷骰的种子必须带上 `还手次数`。只用世界时钟不行 —— 时钟只有 AI 推进时才动，
玩家在同一分钟里连抢几次榜一，同一个种子会算出同一个结果，
**要么每次都还手，要么一次都不还**。这是实装时踩到的坑。

（哈希均匀性单独验过：三成的实测命中率 28.79%，十等分桶都在 10% 附近。）

### 6.2 还没做

- 高能榜上的 NPC 数字只在 `seedRoom` 和还手时动。§5.4 那两条补的是**热度**，
  没有把观众的礼物也记进 `高能榜.本场消费` —— 榜是「谁花了多少」的账，
  弹幕里的观众 ID 是 AI 随手起的名字，记进榜会和种子生成的那批对手混在一起。
- 高能榜的**历史累计**（让榜一像老熟人）没做，只有本场消费。

## 7. 大航海

人数跟体量走（§3 的公式），不跟热度尖峰走。
`seedRoom` 会在名单里放几个具名常客（1~3 个舰长，有提督/总督时各补一个）。

玩家开通舰长/提督/总督：

- 写 `粉丝身份.<名>.牌子档位` 和剩余天数（30 天）。
- `系统配置.直播间.<名>.大航海` 对应档 +1。
- 名单里插入「你」。

**注意区分两条线**：`牌子等级` 是打赏累计换来的（`badgeLevel(累计打赏)`，见 §9），
`牌子档位` 是大航海订阅位。两者无关，开局送的 8 级牌子不带任何档位。

AI 看不到航海名单和人数。叙事里「舰长弹幕优先」只看玩家自己的 `牌子档位`。

NPC 舰长到期、人数微涨微降只在换日时动一点点 —— **未做**。

**图片地址一律不进 MVU**，太占地方。

## 9. 和已有结算怎么接

`roomAction()` 是唯一写入口。一次调用做完这些事：

1. **校验**：主播名认不认识、礼物存不存在、**钱够不够**。
   任一不过就直接返回 `{ ok: false, 提示 }`，**什么都不写**，也不留下连送痕迹。
2. 扣钱、写 `所在直播间`。
3. 花过钱就自动 `关注: true`，`累计打赏 += 花费`，
   `牌子等级 = badgeLevel(累计打赏)`。
4. 大航海：写档位和天数、对应档 +1、名单插「你」。
5. `本场热度 += 连送递减后的人气点数`，重算 `直播.热度`。
6. 高能榜 upsert「你」并重排。
7. 单笔 ≥ 100 才掷骰看榜一还不还手。

牌子等级的公式（`badgeLevel`）：

```
牌子等级 = ⌊20 × (累计打赏 / 200000)^(1/3.5)⌋   上限 20
```

它**只是累计打赏的函数**，不是独立字段 —— 每次变量更新都会被重算。
所以开局页要给 8 级牌子，只能把 `累计打赏` 写成反解值 **8100**
（直接写 `牌子等级: 8` 会在下一次变量更新时被打回去）。

仍然成立：

- 打赏不买好感，热度不是好感。总督不买服从。
- 小心心点了就送不弹窗，几乎不推动热度；花钱的才确认数量。
- 送礼与喜好的其余规则见 `世界书/送礼与喜好`。

---

## 10. 节拍（什么时候算一次）

1. 玩家确认送礼 / 办卡 / 醒目留言 / 关注 → `roomAction()`，立刻算。
2. 玩家进入某间房 → `roomView()`，第一次会 `seedRoom()`。
3. 世界时钟推进 → `VARIABLE_UPDATE_ENDED` 里衰减本场热度、跑开播判定。
4. 换日 → 清今日已上班、扣牌子天数、扣禁言天数、递减近期性经验次数。

不要每条弹幕都算热度。

## 11. 明确不做

- 不把高能榜、航海名单、精确热度塞进世界书或变量注入。
- 不让 AI 生成榜一名字或改 `系统配置`。
- 不把热度做成「金额 × 固定倍数」的直线，也不做无上限滚雪球。
- 不在休播时涨热度。
- 不在展示层（`正文美化.html`）存任何表或数值，也不在那里写 MVU。
- 不把图片地址存进 MVU。
- 不做「在线人数」这个第二个数（见 §5.4）。
